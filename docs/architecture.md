# Архитектура

Три проекта без DI-контейнера, репозитория данных и сторонних union-библиотек:

- `UnionTypes.Demo`: CLI, транспортный `WorkPayload`, доменный `Description`, HTTP-клиент и `FetchResult`.
- `UnionTypes.Legacy`: независимый старый подход к обработке `JsonElement`, nullable-свойства и ручная проверка инварианта.
- `UnionTypes.Tests`: xUnit, локальные fixtures, подменяемый `HttpMessageHandler` и вызовы CLI через `TextWriter`.

Demo ссылается на Legacy исключительно для режима сравнения. Legacy не зависит от новых union-моделей. Транспортный разбор не вызывает доменный mapper; каждый подход самостоятельно обрабатывает одно и то же значение `JsonElement`.

## JSON → транспорт → домен

`System.Text.Json` читает `WorkPayload`. `title` обязателен и должен быть строкой. `Description` имеет тип `JsonElement`: отсутствие поля даёт `Undefined`, явный JSON null — `Null`. При сериализации `WhenWritingDefault` пропускает только значение по умолчанию, поэтому эти состояния различимы после round-trip. `JsonExtensionData` сохраняет неизвестные поля конверта; содержимое объекта description сохраняется целиком.

Стандартный STJ однозначно сохраняет все необходимые формы через `JsonElement`. Собственный `JsonConverter` не добавлен: нет необходимости поручать сериализатору выбор case type или сериализовать внутреннее представление union. Round-trip относится к транспортной модели и семантике JSON, а не к исходным пробелам, порядку свойств или байтам.

`Descriptions.FromJson` создаёт `PlainText`, `TextObject` либо `NoDescription`. Missing и null объединяются, поскольку для показа описания оба означают отсутствие текста. Если позже понадобится PATCH-семантика «не менять» против «очистить», исходное различие остаётся в транспортной модели. Обратное восстановление этой разницы из одного доменного union невозможно.

Числа, bool, массивы, объекты без строкового `value`, с неизвестным `type` либо с null вместо строки отвергаются через `JsonException`. Допустимый объект требует `type=/type/text`. Пустая строка допустима и не заменяет ошибочные данные. Неизвестные поля объекта допустимы. Это выбранный контракт учебного клиента, а не полная схема Open Library. Повторяющиеся имена JSON-свойств не валидируются отдельно: действует поведение STJ (последнее значение).

## HTTP

`HttpClient` передаётся конструктору. `FetchResult` включает успех, JSON redirect, 404, прочий неуспешный HTTP-статус, сетевую ошибку, некорректный payload и timeout. `/type/redirect` распознаётся до чтения WorkPayload: его `location` должна иметь форму `/works/OL<digits>W`. JSON redirect не проходится автоматически; CLI печатает цель и возвращает 0. Это не HTTP 3xx. HTTP-клиент проверяет description до возврата WorkFound. Ошибки не превращаются в пустое описание. Отмена вызывающим кодом пробрасывается как `OperationCanceledException`, timeout возвращается отдельным case.

`HttpResponseMessage` освобождается после чтения. Переданный `HttpClient` остаётся собственностью вызывающего кода. CLI освобождает только созданный им экземпляр. ID проверяется по формату `OL<digits>W`; хост фиксирован. Нет retries и кеширования. JSON читается целиком в память, поэтому это учебный клиент, а не загрузчик больших коллекций.

## Инварианты и ограничения

Legacy-модель допускает одновременно `Text` и `Object`. `Render` обнаруживает конфликт только во время выполнения. Union хранит один case, а exhaustive switch помогает заметить расширение множества вариантов. При этом `default` union всё ещё содержит null; доменный renderer явно отвергает его. `NoDescription` — осмысленный case, а не null-содержимое.

Открытые case records не проверяют содержимое произвольных пользовательских строк. Проверка входных данных выполняется на JSON-границе. В режиме `compare` обе реализации должны возвращать одинаковый текст, а не скрывать ошибки одной за результатом другой.
